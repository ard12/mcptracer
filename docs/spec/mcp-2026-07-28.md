# MCP 2026-07-28 Compatibility

Status: **partial, explicitly versioned support** (T-92A). This is not a claim
of complete 2026-07-28 conformance.

## What changed upstream

MCP 2026-07-28 removes the protocol-level `initialize` handshake and
`Mcp-Session-Id`. Each request is self-describing through `_meta`, and
Streamable HTTP mirrors the protocol version, method, and selected name/URI into
required routing headers. It also introduces MRTR, `server/discover`, cacheable
list results, subscriptions, custom tool-parameter routing headers, and a formal
extension system.

## Shipped in T-92A

### Passive recording

`record-http` already forwards end-to-end headers and message bytes unchanged,
so modern POST requests and request-scoped JSON/SSE responses pass through the
same bounded capture path as legacy traffic. `server/discover`, `resultType`,
cache fields, and extension payloads are preserved as ordinary JSON rather than
being dropped by an era-specific parser.

Because the modern protocol deliberately has no session identifier, the safe
default remains one recording per header-less request: the proxy must not merge
traffic from unrelated clients merely because it arrived during one process
lifetime. A caller that owns a trace boundary can opt into:

```bash
mcptracer record-http \
  --listen 127.0.0.1:8787 \
  --target https://server.example/mcp \
  --group-stateless-by-header X-Trace-Id
```

Requests with the same non-empty `X-Trace-Id` value share a recording. The
value is used only as an in-memory map key and is never persisted or printed;
the header itself is still forwarded upstream like every other end-to-end
header. A `DELETE` carrying the same correlation header explicitly finalizes
the local recording after its upstream response is forwarded. A modern server
will normally answer that DELETE with `405`; its status is not rewritten.
Otherwise the group closes during graceful proxy shutdown.

### HTTP replay

For a request carrying
`params._meta["io.modelcontextprotocol/protocolVersion"]` (or the same key in a
top-level `_meta`), `replay-http` derives these headers from the body:

- `MCP-Protocol-Version` from the metadata value;
- `Mcp-Method` from `method`;
- `Mcp-Name` from `params.name` for `tools/call` and `prompts/get`, or
  `params.uri` for `resources/read`.

`Mcp-Name` uses the specification's `=?base64?...?=` sentinel for non-ASCII,
control/edge-whitespace, or sentinel-looking values. Modern requests never
receive a legacy `Mcp-Session-Id`, even if a mixed source previously caused a
legacy target to return one. Users cannot override these derived headers with
`--header`.

The real integration test records two self-describing stateless requests into
one explicit trace, validates the result, replays it without caller-supplied MCP
routing headers, and proves the sessions diff cleanly.

## Implemented replay slice

For a modern `tools/call`, replay resolves the matching tool from the latest
prior captured `tools/list` response. It derives `Mcp-Param-*` only from
non-empty token annotations on primitive `string`, `integer`, or `boolean`
properties reached solely through `properties`; it omits absent arguments,
uses the standard string sentinel encoding, limits integers to JavaScript-safe
values, and rejects malformed, duplicate, unsupported, or temporally missing
definitions rather than guessing routing headers. Manually supplied
`Mcp-Param-*` values are ignored for these calls.

For captured modern `tools/call`, `prompts/get`, and `resources/read` MRTR
sequences, replay accepts `resultType: "input_required"`, validates that the
next captured request is the same original operation with matching
`inputResponses`, replaces its opaque `requestState` with the target's live
value, and assigns a fresh JSON-RPC id. It fails closed on missing, malformed,
or divergent retry evidence, and bounds a chain to ten rounds.

For captured modern `subscriptions/listen` streams, replay requires the first
SSE frame to acknowledge the captured filter, requires every later frame to
carry that listen request's `io.modelcontextprotocol/subscriptionId`, and keeps
the stream open while later captured requests execute. It rejects unknown core
filter types, missing acknowledgments, untagged or out-of-filter notifications,
and a target stream that produces fewer or more captured notification frames.

## T-92 preservation evidence and support boundary

The full requirement-to-implementation/test ledger, including unsupported and not-yet-tested rows, is here (private record, not distributed).

The modern HTTP integration fixture now sends cache metadata and a namespaced
extension payload in `tools/list`, and sends a namespaced client extension field
in that request's `_meta`. The test checks the upstream response, the persisted
source request/response payloads, replay delivery of the request field, and a
clean source/replay diff. This is evidence that MCPTracer treats these values as
opaque protocol data across capture and replay; it is not evidence that it
implements cache behavior or the extension's semantics.

Cache metadata and extension payloads are captured observations, not immutable
provenance about server behavior. A replay is meaningful only when the recorded
request/response sequence is healthy and complete, and when required routing
context can be derived or supplied by the protocol. MCPTracer does not infer
missing TTL/scope values, negotiate optional extensions, or claim semantics it
has not exercised. Diffs compare the recorded payloads, including cache fields,
and extension data. Changed/missing cache metadata and list-order changes have explicit negative coverage. The explicit list-order negative is exercised at `/tools/0/name`.
